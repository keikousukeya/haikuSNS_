1. 要件仕様書（Requirements Specification）
1.1. サービス概要
ユーザーが「5・7・5」の調べにのせたテキスト（最大17文字＋α）のみを投稿・閲覧できる短文特化型SNS。

1.2. 機能要件 (Functional Requirements)
ユーザー管理

アカウント作成（メールアドレス、またはGoogle/Apple認証）。

プロフィール設定（ユーザー名、＠ID、アイコン、自己紹介）。※自己紹介も575限定にすると世界観が統一されます。

投稿（詠む）機能

厳格な文字数チェック: * スペース区切り、または連続したテキストで合計17文字であること。

より厳格にする場合、形態素解析（MeCab等）を用いて「5音・7音・5音」の音節（モーラ）を判定し、合致しない場合はエラーを返す（※「季語」の有無は任意）。

画像・動画の添付は不可（テキストのみ）。

タイムライン（閲覧）機能

タイムラインは縦書き表示を選択可能（日本文化へのリスペクト）。

「おすすめ」「フォロー中」「最新」のタイムライン。

インタラクション（評価）機能

いいね機能（名称は「座布団」または「あわれ」「をかし」）。

リポスト機能（名称は「唱和」）。

コメント機能（ただし、返信も575でしか打てない仕様）。

1.3. 非機能要件 (Non-Functional Requirements)
低遅延・高スループット: 1データあたりのサイズが極小（数十バイト）なため、タイムラインの読み込みはミリ秒単位で高速化する。

高可用性: バズった際の一時的なアクセス集中（スパイク）に耐えられるアーキテクチャ。

アクセシビリティ: 縦書き表示におけるスクリーンリーダーやブラウザ互換性の確保。

2. 技術スタック（Technical Stack）
レイヤー,選定技術,選定理由
フロントエンド,Next.js (App Router) / Tailwind CSS,縦書きレイアウト（CSSの writing-mode: vertical-rl）の実装が容易。SEOと初期表示速度（SSR/ISR）を重視。
モバイルアプリ,Flutter,1つのコードベースでiOS/Androidに高速展開。シンプルなUIなためクロスプラットフォームと相性抜群。
バックエンド API,Go (Gin) または Node.js (TypeScript / Elysia),17文字のバリデーションと超高速なリクエスト処理に特化するため、軽量かつ高スループットな言語を選択。
形態素解析 (575判定),Kuromoji.js または MeCab (Goラッパー),投稿時に文字数だけでなく「音節（モーラ）」をカウントするための自然言語処理ライブラリ。
メインデータベース,PostgreSQL (Supabase),ユーザーデータやリレーション（フォロー、座布団）を堅牢に管理。Supabaseなら初期開発が超高速。
キャッシュ / TL保持,Redis (Upstash),タイムラインのキャッシュ、および「座布団（いいね）」のカウントなど、高速なインメモリ処理用。
インフラ / ホスティング,Vercel (フロント) / AWS Fargate または Cloud Run (バックエンド),サーバーレス、またはコンテナ運用で、アクセス急増時の自動スケーリングを担保。

3. システムの特徴的な処理フロー（575判定）
ユーザーが投稿ボタンを押した際の、バックエンドでの「575バリデーション」のロジックイメージです。

[ユーザーの入力] -> 例:「古池や かわず飛び込む 水の音」
       |
[APIサーバー (Go/Node.js)]
       |
[形態素解析エンジン] -> 読み（カタカナ）に変換: 「フルイケヤ カワズトビコム ミズノオト」
       |
[音節カウント処理] -> 拗音（ゃ、ゅ、ょ）を除外してモーラ数をカウント
       |
[判定] -> 5音・7音・5音 に分解できるか？
       |-- YES --> データベースに保存・タイムラインへ配信
       `-- NO  --> エラー「五七五になっておりません（字余り・字足らず）」を返す


4. この仕様の面白いポイント
データベースのストレージ消費が激安: 1投稿が最大でも数十バイト（UTF-8）に収まるため、通常のSNSに比べてテキストデータのストレージコストが1/100以下になります。

リプライの民度が高くなる: 文句を言うにも「575」に変換しなければならないため、ネットスラングや感情的な誹謗中傷が生まれにくく、知的な大喜利空間になりやすいです。

5. 追加機能要件（現状実装との差分より・今後の拡張候補）
プロトタイプの実装状況を一般的なSNSに必要な機能と照らし合わせた結果、以下が未実装または部分実装であることが判明した。優先度の高い順に記載する。

5.1. 通知機能（未実装・優先度高）

フォロー・座布団・唱和・返し（コメント）を受けた際に、本人に通知が届く仕組みが無い。相互のやり取りに気づけないため、SNSとしての反応・熱量が伝わらない。

5.2. プロフィール編集UI・フォロワー一覧（未実装・優先度高）

プロフィール更新API（ユーザー名、＠ID、アイコン、自己紹介）は存在するが、それを呼び出す編集画面が無い。

フォロワー一覧・フォロー中一覧を取得するAPI自体が存在せず、「誰にフォローされているか」「誰をフォローしているか」を確認できない。

5.3. 検索・発見機能（未実装）

ユーザー検索、投稿検索、ハッシュタグ／トレンド機能が無く、タイムラインを眺める以外に投稿やユーザーを見つける手段が無い。

5.4. 投稿の編集・削除（未実装）

誤字や字余り・字足らずの許容範囲を超えた投稿を後から編集・削除する手段が無い。

5.5. モデレーション・安全機能（未実装）

通報、ブロック、ミュートの仕組みが無い。

5.6. ダイレクトメッセージ（未実装）

ユーザー間の非公開でのやり取り（DM）機能が無い。

5.7. 投稿詳細ページ・ページネーションUI（部分実装）

投稿詳細を取得するAPIはあるが、個別URLでアクセスできる投稿詳細ページがフロントに無い。

タイムラインAPIは`limit`/`offset`に対応しているが、フロント側は先頭ページのみで無限スクロールや「もっと見る」の実装が無い。

5.8. 運用・セキュリティ基盤（未実装）

レート制限、CORSの許可オリジン制限、HTTPS化、JWT秘密鍵の強制的な環境変数化など、本番運用を想定したセキュリティ強化が未実装。

単体テスト・E2Eテストが無い。

備考: 縦書き表示、Google/Apple認証、自己紹介の575限定、形態素解析による575自動判定、Go/PostgreSQL/Redis等の本格インフラ移行は、既存要件（1.2・2章）に記載済みだが、開発優先度の都合上プロトタイプでは意図的に対象外としている。
